# Native extraction conversions and integration gaps

The approved framework defines desired logical types. Editing a skill does not extend the Python expression parser, plan validator, transport or notebook. Distinguish required conversions from currently executable expressions.

## HANA candidate expressions

ECC-LOCAL uses native HANA SQL. Prefer explicit formats over session-dependent implicit casts. The following native expressions illustrate the conversion policy. Use the exact templates supplied by the workflow prompt; arbitrary variants are not accepted:

| Meaning | Candidate native HANA expression | Expected result |
|---|---|---|
| Valid DATS | `TO_DATE("DATE_FIELD", 'YYYYMMDD')` | Native DATE; display `2026-10-12`. |
| DATS with the approved zero-date policy | `TO_DATE(NULLIF("DATE_FIELD", '00000000'), 'YYYYMMDD')` | SQL NULL for exactly `00000000`; other valid values become DATE. Other invalid values are not implicitly NULL-approved. |
| Valid TIMS | `TO_VARCHAR(TO_TIME("TIME_FIELD", 'HH24MISS'), 'HH24:MI:SS')` | STRING `14:30:25`. |
| Confirmed packed TIMESTAMP | `TO_TIMESTAMP(TO_VARCHAR("TS_FIELD", '00000000000000'), 'YYYYMMDDHH24MISS')` | Native timestamp, no timezone shift. |
| Confirmed packed TIMESTAMPL | `TO_VARCHAR("LONG_TS_FIELD", '00000000000000.0000000')` | Exact STRING preserving all seven fractional digits; no lossy Spark TIMESTAMP. |

Verify function availability and numeric formatting/padding against the actual source release, including fractional digits and absence of scientific/grouped notation. Native format tokens are not Spark patterns. The user explicitly approved NULLIF for DATS exactly `00000000`; preserve TIMS `000000` as `00:00:00`, without NULLIF on that sentinel. Do not extend NULL handling to blanks or other invalid values without a separate policy. Validate representative results and typed Parquet/loader behavior; `WHERE 1 = 0` proves only syntax/acceptance. These expressions remain design templates until parser/runtime support is implemented.

Physical-numeric identifiers require exact native string conversion without rounding, scientific notation or display exits, preserving domain-defined padding. Ordinary DEC/CURR/QUAN/integer/FLTP fields can remain native numeric extraction when transport preserves approved precision/range. Boolean conversion needs an exhaustive domain-specific true/false map, NULL policy and unknown-value treatment. RAW/LRAW/RAWSTRING need verified complete byte transport or a supported exact Base64 encoder/decoder; never invent one.

Use `sap-help`/SAP docs for HANA functions, `abap-docs` for ABAP semantics and `microsoft-learn` for Fabric/Spark. Another SAP database backend needs its own verified native dialect. Client predicates and watermark bounds remain the external pipeline's responsibility, against original identifiers/types.

## Implemented conversion contract

The parser rejects empty/non-digit dates and out-of-range times (including 240000) using shape/range checks inside CASE before native parsing. Only DATS 00000000 becomes NULL; TIMS 000000 remains midnight. Older unguarded templates are retained only for history compatibility, not new proposals. The Python parser now accepts the exact closed templates generated by 	hirdparty/sap/extraction.py: DATE via TO_DATE(NULLIF(field, '00000000'), 'YYYYMMDD'), TIME via TO_VARCHAR(TO_TIME(field, 'HH24MISS'), 'HH24:MI:SS'), short TIMESTAMP via TO_TIMESTAMP(TO_VARCHAR(field, '00000000000000'), 'YYYYMMDDHH24MISS'), and LONG_TIMESTAMP via TO_VARCHAR(field, '00000000000000.0000000'). Use LONG_TIMESTAMP with target STRING for semantically confirmed DEC(21,7) timestamps. This preserves all seven digits, including initial packed zero values, without parsing them into an invalid date or losing precision. This is the selected lossless fallback; do not ask the user the precision question again.

Boolean conversion uses a closed CASE template with NULL preservation, explicit true/false domain values and rejection of unknown values. Copy the exact template from the workflow prompt, not an arbitrary CASE. The app independently reads DD04L domains and DD07L fixed values, and requires the supplied Boolean mapping to match them. It accepts DATE for DATS, formatted STRING for TIMS, and exact STRING for long timestamps. FLTP remains DOUBLE unless a verified exact-string identifier conversion is proposed. Malformed non-sentinel dates/times are rejected by native parsing, not silently replaced with NULL.

	hirdparty/sap/transport.py supplies a typed decoder for the custom endpoint: DATE SQL NULL serialized as empty text becomes None, Boolean 1/0 text becomes bool, exact decimals/integers reject floating-point JSON intermediates, and long timestamp STRING retains every digit. These are field-type-specific rules, not a blanket conversion of empty STRING to NULL. External pipelines must integrate this decoder or equivalent behavior before typed Parquet writes; the migration workflow provisions schema/configuration and does not execute ingestion.

The one-field/one-column contract still excludes raw/remainder companions and TIMESTAMP_NTZ. Arbitrary functions, arbitrary CASE and Base64 encoders remain unsupported. Direct BINARY requires verified byte transport. Existing approved tables are changed only through target-change review; skill edits do not modify them.
